# OTA Phase 0 — release identity, immutable layout, and an approval gate

Status: **foundations landed, not yet exercised on a host.** Nothing in this
document describes a working over-the-air update. Phase 0 makes a safe update
*possible*; the first controlled rollout is what will make it *real*, and until
that has happened OTA must not be described as live to anyone.

## Why this exists

The first design-partner host was found in a state that no amount of careful
updater logic could have made safe:

- The server was started by launchd with its cwd inside the **developer clone**,
  running TypeScript directly through `tsx`. There was no build artifact and no
  release. Whatever files were on disk were what production served.
- That clone was on a feature branch, two commits ahead of `origin/main`, and no
  deployment record mentioned the commit that was actually running.
- Two state files disagreed about the deployed version, and both disagreed with
  the process.
- The updater's own check therefore reported `"upToDate": false` and offered to
  "update" the machine by checking out `origin/main` — which would have
  **reverted** the code being served. Only the fact that unattended apply was
  switched off prevented it.

Two directions of silent failure follow from one root cause: the deploy target
and the working copy were the same directory. A `git checkout` by a person
changed production; an update by the machine discarded a person's work. Phase 0
removes that root cause and adds the identity and consent machinery an Update
button needs.

## What a release is now

A release is a **signed-able tag on `origin/main`**, not a commit and not a
branch. `isAuthoritativeReleaseSource` refuses everything else: a feature
branch, `staging`, a bare SHA, a non-release tag, a tag that is not an ancestor
of main, and any remote other than `origin`.

A release is materialized as an **immutable directory**:

```
<releasesRoot>/v2026.827.2-f552df77/     exported, installed, built, sealed
<releasesRoot>/current -> v2026.827.2-f552df77
```

The export uses `git archive`, so **the release contains no `.git`**. That is
the mechanism, not a detail: there is nothing inside a release for `git
checkout` to act on, so the developer tree and the serving tree can never be
confused again. Rollback becomes an atomic symlink swap back to a directory that
was never mutated.

Dependency install inside a release uses `--frozen-lockfile`. The previous
updater used `--no-frozen-lockfile`, which resolves fresh from the public
registry on the customer's machine at apply time — an unreviewed dependency
fetch on every update. Verified working at `v2026.827.2` and at current main.

## What the board can see, and what it can do

`GET /api/instance/ota/status` is read-only and safe to poll. It performs no
git, no network, and no writes; it reads what the daily check already wrote. It
returns the installed release, the available release with its verbatim notes, a
compatibility verdict, a diff summary, a rollback plan, the current approval,
and a single `canApply` boolean with `blockedReasons` explaining any false.

Approval is a two-step ceremony reusing the shape already established by bridge
enrollment: request, then decide. The approval record is bound to the **commit**,
not just the tag, and stamps the compatibility verdict that was true at the
moment consent was given. If either moves before apply, the approval no longer
authorizes and the operator is asked again.

**There is deliberately no apply route.** The server records that a human said
yes; a separate privileged process observes that record and acts. A process
cannot reliably restart itself and then report on the restart, and putting
deploy authority in the web tier would make every web vulnerability a
code-execution path on a customer's machine. The blast radius of this endpoint
is "wrote a JSON file".

## Database compatibility, stated plainly

Drizzle migrations **have no down-migrations**. There is no `.down.sql` and
nothing in the journal to reverse. So any release carrying a pending migration
is classified `forward_only`: it can be applied, but rolling back afterwards
requires restoring the pre-update backup and accepting the loss of everything
written since.

That is a property of the schema tooling, not of this planner, and the approver
is told it before clicking rather than discovering it during an incident. An
unreadable migration inventory is `unknown` and **blocks** — guessing there
costs a database.

## Release notes for this change

- Releases are identified by tag plus commit, and only `origin/main` release
  tags are accepted as a source.
- Instances can be served from immutable, `.git`-free release directories with
  atomic symlink promotion and bounded retention.
- One canonical deployment state replaces the two that disagreed. Reconciliation
  prefers the **running** commit over any recorded one and records the drift
  rather than hiding it.
- New read-only update-status contract covering version, availability, release
  notes, compatibility, diff summary, and rollback plan.
- New approval ceremony; apply is gated on a commit-bound, verdict-stamped
  human decision.
- Rollback plans now state explicitly whether a database restore is required and
  what data would be lost.

## Manual first-update runbook

Run this on a **non-production instance first**. Until it has been completed
successfully at least once, the OTA path is unproven and the Update button
should stay unused.

### 0. Preconditions

- The instance is on `origin/main` at a tagged release, or you are prepared to
  cut over to one.
- A verified backup exists (`agentdash-backup-db.sh` writes one with a sha256).
- You know which commit is actually running — check the serving process's cwd,
  not a state file.

### 1. Materialize the target release (changes nothing that is serving)

```sh
node scripts/deploy/ota-release-layout.mjs   # library; see the dry-run snippet below
```

Export the tag into the releases root, then install and build inside it. The
running instance is untouched throughout — this only creates a directory.

### 2. Verify the release before promoting it

- `.git` is absent from the release directory.
- `pnpm install --frozen-lockfile` succeeded.
- Package and UI builds succeeded.
- The release directory is sealed read-only.

### 3. Reconcile deployment state

Write the canonical state from the running commit plus whatever the legacy files
say. Confirm `current.commit` matches the process that is actually serving
before going further. If it does not, stop: the host is in the state described
at the top of this document and needs a person, not an update.

### 4. Cut over

1. Take a fresh backup and record its path.
2. Point `current` at the new release (atomic swap).
3. Repoint the launchd service at `<releasesRoot>/current` and set
   `AGENTDASH_RELEASE_DIR`.
4. Restart the service.
5. Wait for `/api/health` to report ok.
6. Write the receipt.

### 5. Roll back, if health does not return

1. Swap `current` back to the previous release directory.
2. Restart and re-check health.
3. **Only if a migration ran:** restore the database from the backup taken in
   step 4.1, accepting the loss of anything written since.

### 6. Prove it before believing it

The rollout is not verified until a deliberate failure has been rehearsed: apply
a release, fail the health check on purpose, and watch the rollback restore
service. An untested rollback is a plan, not a capability.

## Known limitations

- **No signature verification.** Nothing verifies tag or commit signatures yet.
  Trust is still "whatever `origin/main` resolves to over HTTPS". Tag signing and
  `git verify-tag` are Phase 4 and this contract has the field shapes ready for
  them, but the check does not exist.
- **No down-migrations.** See above. Rollback across a migration is
  restore-and-lose-data, not a reversal.
- **The release-source guard exists twice.** Once in TypeScript for the status
  endpoint, once in plain JS for the standalone updater, which must not depend on
  the application's build output. A parity test runs the same case table through
  both and fails on any disagreement, but it is still duplication.
- **The updater has not been rewired to the new layout.** `applyRevision` still
  does `git checkout --detach` in the working tree. Phase 0 provides the layout,
  the guard, the state, and the gate; wiring the apply path to use them is the
  next change, and until it lands the old path is still what runs.
- **Migration identity is positional.** Applied migrations are derived from the
  journal prefix by row count, which is exactly how drizzle decides what to run,
  but it assumes the database was migrated by this codebase. A database ahead of
  the checkout returns `unknown` and blocks rather than guessing.
- **Not exercised on a host.** Everything here is unit-tested and dry-run
  against a disposable copy. No instance has been cut over.
