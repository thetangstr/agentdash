# LDD — Launch Design Document for the comprehensive scope

**Written:** 2026-08-16, evening. Companion to `2026-08-16-roadmap.md` (the what)
and `2026-08-16-decisions.md` (the why). This is the how, for everything, designed
once so the pieces do not interfere.

**Rule of this document:** every design claim that could be checked against the
tree or the running system was checked today and cites its evidence. Open
questions are collected in §9 with a proposed default each — an item is
*executable tonight* if its questions are either answered or have defaults the
reviewer accepts.

**Standing decisions folded in:** local-only error sink (nothing egresses),
admin+member roles, open visibility with per-project restriction (hybrid
enforcement), launch slipped for comprehensiveness.

---

## 0. Architecture in one view

Two new shared primitives carry most of the scope. Everything else is a
consumer. This is the anti-interference move: domains talk to primitives, not
to each other.

```
                        ┌─────────────────────────────┐
  routes / services ──▶ │  authz-core                 │  A1 A2 A3 A4 A8
                        │  role(actor), canEdit(),    │
                        │  visibleProjects()          │  A5 A6 (+ RLS backstop)
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
  anything that     ──▶ │  signals                    │  O1 O3 O6, M3 M4, G5
  notices trouble       │  emitSignal(kind, payload)  │
                        └──────┬──────────┬───────────┘
                               ▼          ▼
                          error sink   alerter (SMTP)
                          (Postgres)   no-op w/o config
```

Ops work (C1–C8) is scripts and plists — no server-code overlap with either
primitive. Packaging (G6) is `package.json` surgery — done last, alone, gated.

## 1. authz-core (A1, A2, A8)

### Facts the design rests on

- `company_memberships.membership_role` is **text, nullable, no enum**
  (`packages/db/src/schema/company_memberships.ts:12`). The collapse is a data
  migration plus code, no DDL on the column.
- One direction predicate exists with two callers by design
  (`server/src/routes/authz.ts:166`). We keep that shape and extend it.
- `normalizeHumanRole("member") → operator` is the live trap (measured earlier).

### Design

**Roles.** Exactly two: `admin`, `member`. One normalization function, applied
at every read of the column:

```
owner, admin                      → admin
operator, viewer, member, <else>  → member
```

Write-side accepts only the two canonical values. The legacy strings never
reach a predicate again — normalization happens at the membership-loading
boundary (actor construction), not in each check.

**Predicates**, all in `authz-core`, no caller re-derives:

| predicate | rule |
|---|---|
| `canSetDirection` | role === admin (existing `local_implicit` and `isInstanceAdmin` escapes unchanged) |
| `canEditResource(actor, {createdByUserId})` | admin, or creator |
| `canManageCompany` | admin |
| member implicit grants | `projects:create`, `agents:create`, `tasks:assign` |

The grantable-permission machinery (`PERMISSION_KEYS`, `canUser`) stays — it
becomes the extension point, not the primary path.

**Migration (data):** map all membership rows and all **pending invite** rows
(Sam and Megan sit at `operator` right now, unaccepted) by the same table
above.

**Known consequence, stated:** `viewer → member` is a power *upgrade* (viewer
was read-only everywhere). Measured: mkboard has one human (owner) and two
pending operator invites; only uat test users are affected. The
`assertCompanyAccess` viewer-read-only branch becomes dead code and is deleted
with its tests updated — dead guards that look alive are this codebase's
recurring failure.

## 2. Ownership and visibility (A3, A4, A5, A6)

### Facts

- `projects` has **no** `created_by_user_id` and only a `company_id` index
  (`packages/db/src/schema/projects.ts:20-40`, measured).
- Blast radius measured earlier: 8 read paths in `projects.ts`, 20 in
  `issues.ts` filter on `companyId` alone; `goals`, `issue_comments`,
  `heartbeat_runs`, `activity_log` would need joins.
- The server pool is `postgres(url)` — **default multi-connection pool**
  (`packages/db/src/client.ts:49`); `max: 1` is only the migration utility
  client. Therefore any RLS actor context MUST be transaction-scoped
  (`SET LOCAL`), never session-scoped — a session `set_config` on a pooled
  connection bleeds across requests.

### Schema

```sql
ALTER TABLE projects ADD COLUMN created_by_user_id text;     -- backfilled, Q9
ALTER TABLE projects ADD COLUMN visibility text NOT NULL DEFAULT 'company';
                                              -- 'company' | 'restricted'
CREATE TABLE project_access (
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  principal_type text NOT NULL,          -- 'user' | 'agent'
  principal_id  text NOT NULL,
  granted_by_user_id text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (project_id, principal_type, principal_id)
);
CREATE UNIQUE INDEX projects_company_name_unique_idx
  ON projects (company_id, lower(name)) WHERE archived_at IS NULL;   -- A6
```

A6 note: mkboard has 0 projects (measured), so the unique index cannot collide
there; the migration checks uat for duplicates before creating and fails
loudly with the duplicate list if any exist, rather than picking a survivor.

### Enforcement — hybrid, two layers

**Layer 1 (primary): one SQL fragment.** `visibleProjectsFilter(actor)` exported
from authz-core, applied to every project-scoped list/read:

```
visibility = 'company'
OR actor is admin
OR created_by_user_id = actor.userId
OR EXISTS (SELECT 1 FROM project_access pa WHERE pa.project_id = projects.id
           AND pa.principal_type = <actor kind> AND pa.principal_id = <actor id>)
```

One implementation, 28+ call sites converted to consume it. A test walks every
route exported from `projects.ts` and `issues.ts` against a restricted project
and asserts the leak shape directly — the falsification is "remove the filter
from one query, the test must name that query."

**Layer 2 (backstop): Postgres RLS on `issues` and `cost_events` only** — the
two tables carrying `project_id` directly, per the accepted hybrid decision.

- Actor context: request handlers that touch these tables run inside a
  transaction opening with
  `SET LOCAL app.actor_role = ...; SET LOCAL app.actor_id = ...`.
- Policy shape (fail-closed **for restricted rows only**):

```sql
ALTER TABLE issues ENABLE ROW LEVEL SECURITY;
ALTER TABLE issues FORCE ROW LEVEL SECURITY;   -- paperclip owns the tables; without FORCE the owner bypasses
CREATE POLICY issues_visibility ON issues USING (
  project_id IS NULL
  OR NOT EXISTS (SELECT 1 FROM projects p WHERE p.id = project_id
                 AND p.visibility = 'restricted')
  OR current_setting('app.actor_role', true) IN ('admin', 'system')
  OR EXISTS (SELECT 1 FROM project_access ...)
);
```

- Unrestricted rows pass with **no GUC set**, so the 55 untouched query sites
  keep working; a restricted row with no GUC set is invisible — that is the
  backstop firing, and it fails closed.
- Migrations and maintenance jobs set `app.actor_role = 'system'`.
- **Write path:** the same predicate as `WITH CHECK`, so an unauthorized write
  into a restricted project fails at the database even if a route guard is
  missed.

**Semantics defaults (Q4, Q8, Q9 — proposed, reviewable):** agents see a
restricted project only via its access list (lead agent added automatically);
member-facing cost rollups exclude projects the member cannot see (admin sees
true totals); existing rows backfill `created_by_user_id` to Titus, the only
human who has ever existed on mkboard.

### Ownership editing (A4)

`canEditResource` gates **projects, agents, goals** (goals are direction —
admin-only already). **Issues stay company-editable**: they are the
collaborative work surface, and ownership-gating them would make cross-member
collaboration impossible. Stated as a decision, not an oversight.

## 3. Observability (O1–O6)

### Facts

- The capture path already builds the complete payload and drops it:
  `captureServerError` opens `if (!target) return;`
  (`server/src/observability/sentry.ts:108`), telemetry is `null` unless
  enabled, and no env file has an observability key (all measured).
- `uncaughtException`/`unhandledRejection` already route into
  `captureServerError` (`server/src/index.ts:1375-1380`).

### Design

**`signals` module** (`server/src/observability/signals.ts`): a tiny in-process
pub/sub. Kinds, fixed vocabulary:

```
server_error | run_failed | run_timed_out | run_stuck
backup_failed | backup_stale | disk_low
budget_warn | budget_stop | mandate_expired
```

Emitters never know about sinks. Subscribers at boot: the error sink (always),
the alerter (config-dependent). This is the seam every later channel (Slack,
UI badge) plugs into without touching emitter code.

**O1 — error sink.** New table:

```sql
CREATE TABLE server_errors (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  fingerprint text NOT NULL UNIQUE,      -- hash(name + message-template + top frame)
  name text NOT NULL, message text NOT NULL, stack text,
  last_context jsonb,
  count integer NOT NULL DEFAULT 1,
  first_seen timestamptz NOT NULL DEFAULT now(),
  last_seen  timestamptz NOT NULL DEFAULT now()
);
```

Upsert on fingerprint. `captureServerError` is **rewired** to write here and
emit `server_error`; the remote Sentry transport is **deleted** (decided:
local only — dead code that looks like an egress path is worse than none).
Message-template fingerprinting strips ids/uuids so "project X not found"
groups as one error, not thousands.

**O3 — alerter.** SMTP (nodemailer or hand-rolled — spec decides after checking
whether a mailer dependency already exists). Reads
`AGENTDASH_ALERT_SMTP_{HOST,PORT,USER,PASS}`, `AGENTDASH_ALERT_{FROM,TO}` from
the env file. **With no config it subscribes and records that it dropped a
signal** — the code ships tonight; only delivery waits on Q1. Debounce: first
occurrence of a fingerprint alerts immediately; repeats within 6h fold into a
digest.

**O4 — health that can fail.** `/api/health` keeps every existing field
(measured shape preserved for current consumers) and adds:

```
status: ok | degraded | fail          db:    { ok, latencyMs }
disk:   { freeBytes, ok }             backup:{ latestAt, ageHours, ok }
runs:   { stuck }
```

`backup.ok` = newest dump < 26h old — which makes the silent-backup-failure
mode visible at last.

**O6 — watchdog.** Interval loop in the server: any run in a liveness state
past its deadline → transition to `timed_out` **through the existing heartbeat
service** (never a raw UPDATE — statuses burned us once already) → emit
`run_timed_out`.

**O5 — silent-failure audit** is a process pass with a checklist (empty catch,
`if (client)` skips, `?? fallback` masks), not architecture; runs after the
sink exists so findings have somewhere to report.

## 4. Cost and runaway control (M1–M5)

### Fact that reshapes M1

**The metering pipeline already exists end to end**: `heartbeat_runs.usageJson`,
`normalizeUsageTotals` (`server/src/services/heartbeat.ts:1297`), UsageTotals
with input/cached/output tokens, and `cost_events` writers in
`inference-gateway.ts` / `usage-billing.ts` (all measured today). **M1 is not
"build metering" — it is "the hermes adapter never populates usage."** The
adapter is a patched npm package (`patches/hermes-paperclip-adapter+0.3.0.patch`),
so M1 = extend the patch (or vendor after G6) to surface hermes's usage data
into run events. Sized as an investigation-first spec: what hermes actually
exposes decides how complete the numbers can be.

### Design

- **M2 — seed policy.** One row: company scope, `billed_cents`, monthly window,
  amount from Q7 (default $500), `notifyEnabled: true`, **`hardStopEnabled:
  false`** — deliberately, because a hard stop on a metric that reads zero is
  decorative today and becomes a *surprise outage* the day M1 lands. Flipping
  it on is part of M1's checklist, written there now.
- **M3 — enforcement.** Pre-run check in the heartbeat scheduler via the
  existing budgets service: warn threshold → `budget_warn` signal; hard stop →
  refuse the run + `budget_stop`. Single enforcement site, at the only place
  runs start.
- **M4 — runaway ceiling.** `AGENTDASH_AGENT_DAILY_RUN_CAP` (default 100/agent/
  day), enforced in the same scheduler site, emits `run_stuck`-class signal on
  trip. Complements the existing concurrency bound
  (`HEARTBEAT_MAX_CONCURRENT_RUNS`, measured), which bounds parallelism but not
  a cheap infinite loop.
- **M5 — attribution.** Read-side only: `cost_events` grouped by agent and
  project; joins the costs page. Depends on M1 for nonzero numbers; ships the
  run-count version first (consistent with the "not measured" honesty already
  built).

## 5. Continuity and operations (C1–C8)

- **C1 — LaunchDaemons.** Extend the existing generator
  (`scripts/deploy/agentdash-mac-mini-launchd.mjs`, which has tests) with a
  daemon mode: writes to `/Library/LaunchDaemons`, sets `UserName: yang` (env
  files under `~yang/.config/agentdash` stay readable), same `KeepAlive`, same
  log paths. Unload agents, load daemons, then **reboot test** — the only
  evidence that counts. Needs sudo with a human present.
- **C2 — restore drill.** Newest mkboard dump → scratch DB → table count and
  row-spot comparison against live. Scripted so it becomes repeatable, not
  a one-off heroic act.
- **C3/C4 — backup copy + encryption.** Backup script gains a post-dump stage:
  `age`-encrypt, copy to `AGENTDASH_BACKUP_DEST`, verify by decrypt + gunzip -t,
  emit `backup_failed` on any error and `backup_stale` from the health check.
  Code ships tonight; the *destination value* and *key custody* are Q2. Until
  answered the stage copies to a second local directory — better than nothing,
  honestly labeled not-off-volume.
- **C5 — log rotation.** `/etc/newsyslog.d/agentdash.conf`: 10MB, keep 5,
  compress, for `~/Library/Logs/agentdash/*.log` (measured: no rotation exists,
  postgres.log already 3.6MB). Postgres's own log via its logging_collector
  settings if the embedded build honors them — verified in the spec, not
  assumed.
- **C6 — TLS.** Decision Q3, three honest options: (a) Caddy/mkcert local CA —
  requires installing a CA cert on Titus's, Sam's and Megan's machines; (b)
  Tailscale — zero cert work, but access now depends on a third-party control
  plane; (c) accept LAN HTTP short-term, documented. No default proposed:
  this changes what happens on client machines, which is not mine to default.
- **C7 — retention.** A pruner job (same scheduler as the watchdog) with
  per-table windows, defaults proposed in Q6: activity_log 365d, heartbeat run
  *events* 90d (run summary rows kept), transcripts 180d, resolved
  server_errors 90d. Every prune emits a count into the activity log — deletion
  that leaves no trace is how retention becomes a coverup.
- **C8 — runbook.** `doc/runbook.md`: restart, logs, restore, health, who to
  call. Written last, from what the other items actually built.

## 6. Agent-specific risk (G1–G6)

- **G6 — packaging (decided, D9).** `adapter-utils` builds to `dist`,
  `exports` point at it, `ensure-plugin-build-deps` mtime guard extends to it.
  **Hard gate unchanged:** full server suite + full UI suite + typecheck + live
  hermes run on uat confirmed sandboxed, else revert. Done **last and alone** —
  it is the only item whose failure mode is "nothing loads."
- **G5 — mandate expiry.** Spec opens with a probe (is expiry enforced anywhere?
  — I found the column, not an enforcement site, and absence of a grep hit is
  not absence of logic). If unenforced: check at the scheduler run-start site
  (same seam as M3/M4), refuse + `mandate_expired` signal.
- **G3 — exercise the approval path.** Scripted on uat: an approval-requiring
  action driven pending→approved→executed and pending→denied, reading the DB
  back at each step. 0 approvals have ever existed (measured); this either
  proves the mechanism or produces the defect list.
- **G1 — prompt injection.** Scoped honestly: full hardening is its own
  project. Tonight's slice: (a) fence untrusted content (issue bodies,
  comments) in prompt assembly as explicitly-demarcated data with a
  treat-as-data instruction; (b) a canary corpus (issues containing embedded
  instructions) run against a uat agent, results recorded — a measurement, not
  a guarantee; (c) the standing rule, written into G2's design: **no connector
  goes live without per-action scoping**.
- **G2 — connector scoping.** Design-only tonight (0 connectors exist, so this
  is a gate on a door not yet open): connector registration requires an
  `allowedActions` list and an approval-required flag per action class;
  default-deny for actions not listed.
- **G4 — stewards.** Data: Titus stewards all five unstewarded agents today;
  reassignment is one row later. No code.

## 7. Non-interference: lanes, files, migration ledger

Four lanes, near-disjoint file sets, so specs cannot collide:

| lane | items | files touched |
|---|---|---|
| **1 authz/visibility** | A1 A2 A3 A4 A5 A6 A8 | `routes/authz.ts`, actor construction, `routes/projects.ts`, `routes/issues.ts`, cost read paths, `packages/db` schema+migrations |
| **2 observability** | O1 O3 O4 O6, M2 M3 M4, G5 | new `observability/*`, `middleware/error-handler.ts`, `index.ts` (boot wiring), heartbeat scheduler (one seam), one migration |
| **3 ops** | C1 C2 C3 C4 C5, G4 | `scripts/deploy/*`, plists, newsyslog, backup script — no server code |
| **4 packaging** | G6 | `packages/adapter-utils/*`, esbuild, build-deps guard — last, alone, gated |

Only genuinely shared surface: the **heartbeat scheduler run-start seam**
(lanes 2's M3/M4/G5) — designed as one function, `preRunChecks(run)`, so three
checks land as one edit. And the **migration ledger**, reserved now, applied in
this order regardless of which lane finishes first:

1. role collapse (data: memberships + pending invites)
2. projects ownership + visibility columns + `project_access`
3. unique name index (with dupe pre-check)
4. `server_errors`
5. RLS enable/force + policies on `issues`, `cost_events`

Within lane 1 the order is forced (ownership before restriction before RLS);
lanes are otherwise independent and any can revert without unwinding another.

## 8. Testing doctrine (unchanged, restated as design)

Every guard is falsified — revert the change, the test must fail, and the six
session rules hold (probe live before/after, 400 is inconclusive, read the DB
back, believe tests that push back, report what was not done). Specific to this
scope:

- **Leak test for A5:** a restricted project + a non-member actor, walked
  against every list/read route in `projects.ts` and `issues.ts`; the test
  enumerates routes from the router so a new route cannot be silently missed.
- **RLS backstop test:** deliberately query a restricted row with no GUC set —
  must return empty; with `app.actor_role='system'` — must return the row.
- **Signals test:** each emitter fired once, sink row read back from Postgres.
- **Manual layer stays human:** the reboot test (C1) and the browser walkthrough
  are Titus's/yang's; listed, not claimed.
