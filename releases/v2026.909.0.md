# v2026.909.0

> Released: 2026-09-09 as v2026.909.0.

One squash past v2026.908.0, and no new migration.

**Read v2026.908.0's notes as part of this one.** That release was cut but never
applied to any instance, so everything it describes ships here for the first
time.

**Whether this release migrates depends on what you are running now, not on the
previous tag.** `0127_company_evaluator_ledger` is the only migration in the
range from v2026.904.0, and it arrived in #612 — so any build from #612 onward
already contains it and already applied it at startup. Check the target's
journal tip before assuming: an instance still on v2026.904.0 is applying 0127
here and inherits its rollback consequence (additive, no Drizzle
down-migration, so going back means restoring the backup taken beforehand),
while an instance already past #612 has nothing new to apply. The OTA updater
refuses a migrating release unless run with `--allow-migrations`, and that
refusal is worth reading rather than reflexively overriding — on an instance
with nothing pending it will not fire at all.

Measured on the MK instance before this release: journal tip
`0127_company_evaluator_ledger` in both the installed build and the target, 128
migrations applied in the database, and the three `evaluation_*` tables already
present. No migration to apply there.

## Behaviour Changes

**The connect command no longer assumes one address fits everybody.** This
instance has three doors and none serves everyone: plain HTTP on the office LAN,
which is the only one a client user on a managed Mac opens with no IT ask; the
tailnet address, which has a real certificate but is reachable only from the
tailnet; and the LAN name over TLS, whose private root a managed Mac will not
trust. `PAPERCLIP_PUBLIC_URL` is a compromise picked for the majority, and My
Agent handed it to everyone — including someone who had demonstrably reached the
server by a different address, since they were reading the page through it.

When the published address and the one in the address bar agree, nothing
changes and no control appears. When they differ, both are offered. The
published address stays selected by default, because the command is a thing
people forward and a URL captured from whichever door happened to be open ends
up in a colleague's `~/.codex/config.toml`, working here and silently failing
anywhere else.

This does not fix the underlying split — one variable is still serving two
audiences because no single name resolves everywhere with a trusted certificate.
GH #547 layer 4a retires the choice rather than presenting it.

**Pinning the scheduled-check conversation is now an explicit step.** The
schedule belongs to one conversation, so losing that conversation stops the
checks — and that failure reads as "the agent stopped telling me things" rather
than as a setup step somebody skipped. The page now says to pin it, says it is a
right-click, and says there is nothing to paste for it, because a prompt cannot
pin its own conversation. The existing caveat stands: the schedule lapses after
about a week whether pinned or not.

**The harness preview is gone from My Agent.** It rendered a recreated Claude
Code and Codex interface — MCP status panel, tool-call rows, a composer, the
tool count an agent key carries — next to a section about how to set the check
up. It showed what a connection looks like to somebody who already has one.
