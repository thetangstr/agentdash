# One UX for every company

2026-09-30 · Status: **decided** (founder) · Supersedes decision 2 in [2026-09-26-ux-sharpening.md](2026-09-26-ux-sharpening.md) ("six items … for the default profile and hosted boxes only; the MK profile keeps its current layout").

## Decision

Every company and every user sees the same UI, at least for now. The UI does not branch on `productProfile`.

1. **One shell.** Six primary items for everyone: Home, Ask, Work, Decisions, Shipped and Team. Team has the collapsible Agents list. Everything else goes under Advanced. Instance links show only to instance admins. *(Superseded the same day by the founder's sidebar IA: "Advanced" became a collapsed "More" group — Goals, Routines, Costs, Activity — plus a footer Help menu — Guides, Changelog, Health — and the Settings gear, which opens one grouped Settings navigation: Workspace, Agents, Data, Quality, Account, and Instance for instance admins. Org is a tab on Team.)* That check is based on who the user is, not on the profile.
2. **One landing page, the merged Dashboard at `/dashboard`.** At the top, Home's *Waiting on you / Working now / Shipped*. Below that, the Overview control-plane panels: agents, spend, activity and live runs. This is the right landing page for admins as well as new users.
3. **One version of each page.** Where a page has a default-profile version and an MK version, the newer default-profile version wins: Decisions, Costs (UX-15), Agent detail (UX-14), empty states and copy. The MK Inbox and steward items move into Decisions.
4. **MK capabilities stay gated on the server only.** Stewardship, connector_send, HubSpot/SharePoint, the bridge, directives, the override and steward inboxes, and agent ceilings keep their server-side `productProfile` gate for now. The UI does not hide their entry points. Where a capability is off for the company, its page shows an "available on request" empty state. Behaviour does not change for any existing customer.
5. **Rollout.** Ship in the next stable after v2026.930.1. MKThink gets it only when they apply that release. The founder sends Titus a short what-changed note alongside the release notes.

## Rule going forward

- No new `productProfile` / `agentdash_mk` checks in `ui/src`. A CI guard enforces this with an allowlist that must shrink, not grow.
- A UX change reaches every company. If something must not reach a customer yet, hold the release, not the code path.
- Server capability gates are allowed and must use `requireProductProfile`. Treat them as capability checks, not UX.

## Why

Profile-driven UX meant two apps in one codebase: 61 UI files branch on the profile, and every UX PR had to be built and tested twice. It also let a company's profile decide which PRs it effectively picked up, which is not manageable at our size.
