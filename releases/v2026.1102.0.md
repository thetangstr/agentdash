# v2026.1102.0

> Released: 2026-11-02.

An agent can now set up AgentDash Cloud for a person over MCP: start the signup, wait for the person's approval and connect to the new box, then continue with the setup tools. The cloud control plane also pages a person when a provisioning job fails, and says so when nobody would be paged. Self-hosted installs and boxes get no database migrations and no server or UI behavior changes.

## Highlights

- **Cloud MCP toolset.** `AGENTDASH_TOOLSET=cloud` adds `agentdash_cloud_check_name`, `agentdash_cloud_start`, `agentdash_cloud_status` and `agentdash_cloud_connect`.
  - The agent starts a signup for a person and polls its status with a handle.
  - When the box is ready, the person signs in on the box's approval page, checks the confirmation code the agent shows, and approves. The stdio session then upgrades in place to the box and continues with the setup tools: interview, plan and hire.
  - The person verifies their email, sets their password and approves the agent; no secret passes through the agent.
  - The same tools are served over streamable HTTP at `POST /api/cloud/mcp`. ([#1112](https://github.com/thetangstr/agentdash/pull/1112), @thetangstr)

## Improvements

- **Agent signups are gated.** An agent handle (`agdh_` plus 32 random bytes) is returned once, stored only as a hash, bound to one signup, valid for 7 days, and rate limited per handle and per address. An agent signup without a hosted admission code waits for operator approval; a valid code approves it once the person verifies their email. The existing waitlist, kill switch and daily cap still apply. ([#1112](https://github.com/thetangstr/agentdash/pull/1112), @thetangstr)
- **Operators can see whether anyone is paged.** `admin fleet status` (`GET /internal/fleet/status`) reports `alerting: { transports, paging }`, and cloud-control warns at boot when the log is the only place alerts go. ([#1113](https://github.com/thetangstr/agentdash/pull/1113), @thetangstr)

## Fixes

- **A failed provisioning job pages a person.** Alert email used to need `CLOUD_ALERT_EMAIL_FROM` as well as the recipient and the Resend key, and stayed silently off without it. It now falls back to the front door's verified sender, so `CLOUD_ALERT_EMAIL_TO` with `CLOUD_RESEND_API_KEY` turns paging on. An explicit `CLOUD_ALERT_EMAIL_FROM` still wins. ([#1113](https://github.com/thetangstr/agentdash/pull/1113), @thetangstr)
- **Signup no longer reveals whether an email has an account.** An existing or blocked email now records a decoy signup, so a name looks held either way. This also closes the same leak on the browser signup path. ([#1112](https://github.com/thetangstr/agentdash/pull/1112), @thetangstr)

## Upgrade Guide

- **Self-hosted installs and boxes:** no application migrations, and no server or UI behavior changes. The release adds the MCP server's `cloud` toolset and documentation.
- **cloud-control operators:**
  - Migration `0014_agent_handles` must apply to the cloud-control database before cloud-control starts; cloud-control refuses an unmigrated schema.
  - Set `CLOUD_ALERT_EMAIL_TO` (with `CLOUD_RESEND_API_KEY`) or `CLOUD_ALERT_WEBHOOK_URL`, then check that `admin alerts test` reports `email` or `webhook` with `ok: true` (`doc/runbooks/cloud-control-plane.md`).
- **Known limit:** the box's approval page still says "Paperclip CLI".
