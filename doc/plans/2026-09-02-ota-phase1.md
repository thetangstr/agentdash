# OTA Phase 1 — the apply path, and a button that tells the truth

Status: **implemented and proven against disposable targets. Not yet run on any
real host.** OTA is not live and must not be described as live until a first
controlled rollout has been completed and observed.

Phase 0 made a safe update *possible* — release identity, immutable layout, one
canonical state, a consent gate. Phase 1 is the part that actually moves an
instance, plus the screen a person uses to decide.

## The apply path

One orchestrator, `scripts/deploy/ota-apply.mjs`, run by launchd — never by the
server. A process cannot restart itself and then report on how the restart went,
and deploy authority in the web tier would make every web vulnerability a
code-execution path on a customer's machine.

Stages, in this order, because the order *is* the safety property:

```
provenance → direction → approval → compatibility → backup
→ materialize → switch → restart → health → (rollback) → receipt
```

Everything that can refuse refuses **before** anything is mutated. Materializing
and building happen before the switch, so a build failure costs a directory
rather than an outage. The switch is a symlink `rename(2)` — atomic, and
reversible by doing it again in the other direction.

### The direction guard, and why it exists

`assessUpdateDirection` refuses a target that is not a descendant of the
installed commit. This is not theoretical caution. On this repository **every
`v2026.827.x` tag resolves to the same commit** (`f552df77`), and that commit is
*behind* `origin/main`. "Apply the newest release" is therefore not automatically
forward motion, and without this guard an update could quietly revert a host —
which is the precise failure the whole release-identity effort set out to end.

- descendant → `forward`, allowed
- identical → `same`, reported as a no-op, nothing touched
- ancestor → `backward`, **refused**; use an explicit rollback
- unrelated → `diverged`, **refused**; neither an update nor a rollback

### Migration policy

**Refused by default.** Automatic rollback restores code. A release that migrates
the database cannot be undone by moving code back, so applying one unattended
would mean advertising a rollback that does not exist.

`--allow-migrations` exists for an operator who has read the plan and taken a
backup they intend to use. An unreadable journal on either side is `unknown` and
blocks — guessing there costs a database.

Migration comparison is done by diffing the two checkouts' journals rather than
querying the database, which keeps the updater standalone. It is the tool you
reach for when a deploy has gone wrong; it must not need the application's
database to be reachable.

### Rollback

On failed health: swap `current` back, restart, re-check. Outcome is
`rolled_back` when the previous release comes back healthy, and `failed` with
"Manual recovery required" when it does not. A first-ever deploy with nothing to
fall back to fails loudly rather than silently.

### Receipts

Written on every outcome, including failures — a rolled-back update that left no
record is indistinguishable from one that never ran. State advances **only** on
`applied`; a rollback leaves the recorded current release where it was.

Every receipt carries `signatureVerified: false`, so the limitation lives in the
audit trail rather than only in a document somebody may not have read.

## The client screen

`ui/src/pages/InstanceUpdates.tsx`, at `/instance/updates`.

Shows the running version and whether it is serving from an immutable release or
a developer checkout; the available release with verbatim notes and a diff
summary; the database compatibility verdict with the migrations that would run;
and the rollback plan **before** the button, not after.

The design rule: never look more certain than the server is. `canApply` and
`blockedReasons` are rendered as the server computed them rather than
re-derived, because a button that offers an update the updater will refuse is
worse than no button. Approval takes an explicit confirmation dialog that
restates what will happen — including, when relevant, that rollback restores
code only.

The unsigned-provenance notice is always on screen and never behind a
disclosure. Someone approving a code change on their own hardware is entitled to
know that provenance is unverified.

## Evidence

Unit: 31 tests in `scripts/deploy/ota-apply.test.mjs` with every side effect
injected, including recorded stage ordering (a backup taken after the switch
backs up the wrong thing). 12 in `ota-release-layout.test.mjs`. 9 UI tests
asserting the page refuses to overstate.

Disposable-target dry runs, real filesystem and real `git archive`:

- **Rollback proof** — two releases at distinct commits, health failing only on
  the new one. Outcome `rolled_back`, `current` back on the previous release,
  and the marker file on disk confirmed the *served code* reverted.
- **Happy path** — same target, healthy. Outcome `applied`, marker advanced.
- Checks recorded in order for both, ending `rollback_health:passed` and
  `health:passed` respectively.

## Known limitations

- **No signature verification.** Provenance means "this tag is on origin/main
  and resolves to this commit". Nothing checks who signed it; a compromised
  upstream push would not be detected. Recorded on every receipt and shown on
  the page.
- **Not run on a real host.** Everything above is unit-tested and dry-run.
- **The service repoint is a one-time bootstrap step**, not part of the apply
  path. Pointing launchd at `<releasesRoot>/current` needs root and happens
  once; after that every update is a symlink swap plus a restart.
- **No down-migrations exist**, so `forward_only` really does mean
  restore-and-lose-data.
- **The release-source guard is duplicated** in TS and plain JS, held together
  by a parity test, because the standalone updater must not depend on the app's
  build output.
- **Release tags are currently not distinct commits.** Three `v2026.827.x` tags
  share one commit and the newest is behind main. The direction guard makes this
  safe rather than silent, but the tagging practice upstream needs attention
  before the button is useful — today the newest tag would be refused as a
  downgrade on an instance running current main.
