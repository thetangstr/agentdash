# v2026.902.0

> Released: 2026-09-02

## Behaviour Change You Must Read First

**Newly created agents are now born awake.** `heartbeatEnabled` defaulted to
`false`, so the Run Policy toggle silently pre-answered "no" and every agent was
created switched off. Nothing said so; the only symptom was an agent that never
did anything. On one instance five of six agents were off months after creation,
including the company's primary agent.

The default is now `true`. **A newly created agent therefore starts working, and
spending, without a second action.** Turning it off is one click and is now a
visible decision rather than the absence of one. Agents auto-provisioned for a
new member stay off until their person connects a harness.

Review your agent budgets before creating agents on this version.

## Governance Reaches the Runtime

- **`hermes_local` now delivers the managed instructions bundle.** Previously it
  declared no bundle support, so an agent's `AGENTS.md` was stored, displayed as
  configured, and never sent to the model. Agents on that adapter ran with no
  mandate at all. Capability, backfill for existing agents, and the Instructions
  UI are in this release.
- **Per-agent model binding.** A hermes agent's configured model is now passed
  explicitly rather than inherited from whatever the host's local config
  happened to say.
- **A paused agent no longer escalates past its own pause.**

## Truthful Signals

Four fixes sharing one shape — a green signal that meant less than it appeared.

- **Run health is measured, not claimed.** Every health indicator on an agent
  was a claim made before the fact. The run records knew better: one agent had
  failed 163 of 304 runs and left no evidence on 114 of the 137 that succeeded.
  Agent detail now carries `runHealth`, and the companies list carries a
  `runsSucceededWithoutEvidence` ratio. Expect that ratio to look bad on
  existing fleets — it is the true number surfaced for the first time, not a
  regression.
- **`PATCH /agents/:id` no longer lies about stewards.** It answered `200` to a
  `steward` field and changed nothing, because zod stripped the undeclared key
  before the handler saw it. It now returns `422` and names the real endpoint.
- **Agents can resolve a person.** `GET /companies/:id/people` returns identity
  only — no assignment authority — so an agent asked to act on someone by name
  no longer has to guess an email and then report a colleague as not being a
  member.
- **Expired approvals leave the inbox.** Open was filtered on status alone,
  while nothing marks a lapsed approval as expired, so an approval past its
  expiry sat there as actionable for ever and deciding it did nothing.
- **Mandate rule: do not state what you could not check.** A failed lookup is
  not a finding.

## Over-the-Air Updates: Foundations and Apply Path

This release contains the OTA machinery. **It is not live and has not been run
on any instance.** Do not treat the presence of these features as a working
update path.

- A release is identified by a tag on `main` plus its commit — never a branch or
  a bare SHA.
- Releases materialize into immutable directories via `git archive`, so a
  release contains no `.git` and cannot be checked out. Promotion and rollback
  are atomic symlink swaps.
- Dependency install inside a release uses `--frozen-lockfile`.
- One canonical deployment state replaces the two that previously disagreed;
  reconciliation prefers the observed running commit over any recorded one.
- Read-only `GET /api/instance/ota/status` exposes installed version, available
  release with verbatim notes, a diff summary, database compatibility, and a
  rollback plan.
- Approval is a request/decide ceremony bound to the commit and stamped with the
  compatibility verdict at consent time. **There is no apply route** — the
  server records consent; a separate privileged process acts.
- The apply path runs provenance → direction → approval → compatibility →
  backup → materialize → switch → restart → health → rollback → receipt.
  Everything that can refuse refuses before anything is mutated.
- A **direction guard** refuses a target that is not a descendant of the
  installed commit, so an update cannot silently revert a host.
- Client screen at `/instance/updates`.

### Limitations, stated plainly

- **Release signatures are not verified.** Provenance means the tag is on `main`
  and resolves to this commit. Nothing checks who signed it, so a compromised
  upstream push would not be detected. This is recorded on every receipt and
  shown on the update screen.
- **Migrations are refused by default.** Automatic rollback restores code only.
  There are no down-migrations, so a release carrying a migration can be applied
  but cannot be reversed by moving code back — rolling it back requires
  restoring the pre-update backup and losing whatever was written since.
- **Never exercised on a real host.** Unit-tested and dry-run against disposable
  targets only, including an intentionally failed health check that rolled back.

## Held Back On Purpose

**The inbox read-state narrowing is not in this release.** Counting a read-state
row as participation means opening an issue enrols you in it permanently, so the
inbox still cannot reach zero. Removing that clause is correct for the browsing
case — but the routines service places a coalesced routine issue into the
*manual runner's* inbox by writing a read-state row, and that is genuine
participation. Dropping the clause took the feature out along with the noise.

The table is doing two jobs. The fix is to give "deliberately placed in your
inbox" its own signal instead of overloading "I looked at this", which is a
schema change and is tracked as a follow-up. A noisy inbox is the lesser of the
two failures.

Also not included: making the wake choice **required** at creation.

## Upgrade Guide

This is an in-place source upgrade. Preserve the existing database,
configuration, storage, and agent data; do not reinstall or reimport the
instance.

Back up the database first. Allow the normal startup migration path to apply
only pending migrations. On any post-restart failure, use the rollback wrapper.
Do not run ad hoc `git pull`, replace the installation, or restore a database
backup without explicit operator approval.

If your instance serves from a working checkout rather than a pinned release,
migrate it to the immutable release layout before relying on any update path. An
instance whose checkout has diverged from `main` will be refused by the
direction guard, which is the intended behaviour.
