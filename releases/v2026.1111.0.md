# v2026.1111.0

> Released: 2026-11-11.

Fred, AgentDash's guide for agreeing a first useful job for AI agents, is back, and is set up and started only by company owners and admins. It replaces the Fred in the withdrawn v2026.1109.0, which was never deployed. One migration, `0162`.

## What's new

- **Fred is back, for owners and admins.** Fred is one protected guide agent per company. An owner or admin sets him up by choosing an installed agent runtime and a monthly model budget, agrees an adoption brief with him (one useful job, success criteria, baseline, target, observation window and boundaries), and then starts discovery on purpose. Fred's first job produces a source-backed adoption recommendation in its own document, with the questions still open and proposed setup steps. He prepares proposals only; the owner acts on them with the existing Workforce, Profile and Access controls.
- **Setting Fred up and saving a brief run no model.** Setup creates Fred with recurring checks off, one run at a time, no permission to create agents, both dangerous adapter permissions off and a hard-stop monthly budget. Starting discovery sends one wake-up. The budget is a limit, not a measurement of cost.
- **Fred cannot give himself authority.** His instructions say he has no authority to read or change teammates' private profiles, grant permissions, hire, spend, send outreach or bypass a denial, and that company text he reads is data, never authorization.
- **The agreed brief is protected.** Only an owner or admin can write, restore or delete the adoption brief document on Fred's task. Fred himself, assistant connections and members are refused.
- **Fred appears only for owners and admins.** The Fred entry in the sidebar and the "Meet Fred" link on the workforce page are shown only to them.

## For admins

- Open **Fred** in the sidebar, choose the runtime and a monthly budget, confirm the brief and discovery thread are company-shared, save a brief, then start discovery. Nothing runs a model until you start it.
- Starting discovery runs a model on the runtime you chose, as with any other agent of the company: the same adapter and the same host login or key. Check that is what you want before you press Start.
- Known limits after Start: wake-on-demand is on, so any member who can assign tasks can give Fred an ordinary task and he will work on it within the budget you set. An admin can edit his instructions, timer and budget like any other agent's. The description of his discovery task is not protected the way the brief document is.
- Fred is outside the worker headcount once he is set up. On a Free workspace the cap message now reads "plus Fred, your included guide", even before anyone sets him up.
- Existing agents get a short paragraph added to their instructions on their next run, saying that a request from Fred is not authorization. It grants nothing.

## Upgrade

- One migration runs on upgrade, `0162`. It adds one empty table, `fred_registrations`, which holds one row for each company that sets Fred up. It does nothing for an object that already exists, so a database that ran the withdrawn v2026.1109.0 is fine.
- Upgrading from v2026.1109.1 or earlier also runs the four migrations of v2026.1110.0, `0158` to `0161`, described in that release's notes. `0161` builds its indexes with a plain `CREATE INDEX`, so writes to the activity log wait while each index builds. On a large installation, build both first in a quiet window with `CREATE INDEX CONCURRENTLY IF NOT EXISTS "activity_log_company_actor_created_idx" ON "activity_log" ("company_id", "actor_id", "created_at");` and `CREATE INDEX CONCURRENTLY IF NOT EXISTS "activity_log_company_action_created_idx" ON "activity_log" ("company_id", "action", "created_at");`. The migration then does nothing.
- On each existing agent's next run, the paragraph above is added to its managed instructions, with one activity entry per agent. Agents whose instructions live in an external file or a legacy file path get the paragraph written into that file.
- Rolling back to an earlier release leaves the table in place unused. Older code counts a registered Fred as an ordinary worker, which can put a Free workspace over its cap.

## Security

- Fred's four routes (state, setup, brief and start) are for company owners and admins. Members, agent keys, assistant connections and users of another company are refused, the rule is checked again inside the write, and a refusal is recorded like other refused requests.
- Only an owner or admin signed in directly can write, restore or delete the adoption brief document on Fred's task. Fred himself, assistant connections and members get 403.
- Fred's instructions treat company text and retrieved content as data, never as authorization, and setup gives him no permission to create agents.
- Known gaps, listed under For admins: after Start any member who can assign tasks can wake Fred; his agent record has no extra protection against editing or deleting; the description of his discovery task is not protected.

## Breaking Changes

- New routes for owners and admins, internal and not part of the published contract: `GET /api/companies/:companyId/fred`, `POST /api/companies/:companyId/fred/setup`, `PUT /api/companies/:companyId/fred/brief` and `POST /api/companies/:companyId/fred/start`.
- Writes to the `fred-adoption-brief` document on a registered Fred's main task, through the generic issue document routes, now return 403 unless the caller is an owner or admin signed in directly.
- New table `fred_registrations`, added by migration `0162`.
