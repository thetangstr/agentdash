# v2026.827.3

> Released: 2026-08-27

## Native Backup Delivery Correction

- **Backups no longer require `pg_dump` on the machine** — The generated `agentdash-backup-db.sh` previously hard-required a `pg_dump` executable found through a fixed absolute-path list and exited before touching the database. A native installation on the embedded PostgreSQL distribution has no `pg_dump`, `pg_restore`, or `psql` at all (the embedded package ships only `initdb`, `pg_ctl`, and `postgres`), so the mandatory pre-upgrade backup could never be created and every upgrade failed closed. The wrapper now runs a Node backup runner that uses a compatible `pg_dump`/`pg_restore` pair when one exists and otherwise the repository's own backup engine (`packages/db/src/backup-lib.ts`, the same code the nightly launchd backup already uses on native hosts).
- **Executable compatibility is validated, not assumed** — The runner reads the running server's major version through the checkout's own PostgreSQL driver and only uses a `pg_dump` whose major version is at least the server's, with a `pg_restore` of the same major. An explicit reviewed `PG_DUMP_BIN`/`PG_RESTORE_BIN` override is honoured and validated the same way; `AGENTDASH_BACKUP_ENGINE=pg_dump` or `=javascript` requires a specific engine. A host whose Homebrew `pg_dump` is older than the embedded server no longer fails with a version mismatch mid-upgrade.
- **Every backup is validated before it counts** — Custom-format dumps are checked with `pg_restore --list`. Repository-engine archives are restored into a throwaway database on the same server and every table's row count is compared with the counts recorded in the archive, after which the throwaway database is dropped. The repository engine refuses to run while heartbeat runs are running because it reads tables sequentially.
- **Backup readiness is proven before any mutation** — `agentdash-backup-db.sh --check` is a read-only probe that prints one JSON line (engine, server major, connection source, tool verdicts, searched locations, remediation) and never prints the database URL. The update wrapper runs it before writing pending rollback state, then creates and validates the backup before any checkout, dependency install, build, env pin, or launchd restart, and refuses to continue without the verified archive. Readiness uses the same probe instead of `psql`. A failed probe names the supported overrides, the searched PATH, and the repository-engine remediation.
- **Receipts carry integrity without secrets** — Each archive gets a mode-600 `<archive>.receipt.json` with path, mode, size, SHA-256, engine, server major, and validation result; `deployments/last-backup.json` records the last verified archive; the deployment receipt now includes `backupSha256`, `backupEngine`, and `backupReceiptPath`. No credential is placed on a command line and `/tmp` is no longer used.

## Application Payload

The application payload remains exact source `f552df77417143fd6a949eff8553b98578317f5e`, unchanged from `v2026.827.2`. This patch changes only reviewed release-control logic (the native launchd wrapper generator), its regression coverage, and documentation.

## Upgrade Guide

This remains an in-place source-checkout upgrade. Preserve the existing database, configuration, storage, and agent data; do not reinstall or reimport the instance.

Download these assets from this GitHub Release:

- `agentdash-mac-mini-source-launchd-v2026.827.3.mjs`
- `agentdash-mac-mini-source-launchd-v2026.827.3.mjs.sha256`
- `agentdash-release-control-v2026.827.3.json`

Verify the updater checksum and confirm that the manifest records source SHA `f552df77417143fd6a949eff8553b98578317f5e`. Run the downloaded control script without `--write` first and review the printed plan. Then run it with `--write` while the currently installed SHA remains pinned; this only refreshes the wrappers. Validate every generated shell with the macOS system Bash.

Before changing anything, prove backup readiness and take the backup:

```sh
~/.agentdash/bin/agentdash-backup-db.sh --check
~/.agentdash/bin/agentdash-backup-db.sh
```

The probe must print `"ok":true`. The backup must print a JSON summary with a non-zero `sizeBytes`, a `sha256`, `"mode":"600"`, and a `validation` block; record that summary and the receipt path. If the probe fails, follow the printed remediation; do not pass `--branch`, edit the wrapper, or run ad hoc backup commands.

Then invoke `agentdash-source-update.sh` with the exact target SHA. The wrapper repeats the probe, writes pending rollback state, creates and validates a fresh backup, checks out the pinned source, installs and builds, pins the source in the runtime env, restarts only the configured launchd label, runs readiness, and writes a mode-600 receipt naming the verified backup and its SHA-256. A healthy HTTP response without a successful wrapper exit and receipt is not an accepted upgrade.

Allow the normal startup migration path to apply only pending migrations. On any post-checkout failure, invoke the generated rollback wrapper; it takes its own validated backup before returning to the previous SHA and uses pending state when no prior success receipt exists. Do not run ad hoc `git pull`, replace the installation, or restore a database backup without explicit operator approval.
