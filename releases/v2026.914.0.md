# v2026.914.0

> Released: 2026-09-14 as v2026.914.0.

Two squashes past v2026.909.2. No migration; the journal tip is unchanged, so
applying this is a symlink swap and a restart. This release changes the server,
so a UI-bundle swap cannot pick it up.

**This release is half of a pair.** The other half is `agentdash-connect@0.2.0`
on npm (tag `agentdash-connect-v0.2.0`), and the order matters: the npm publish
must land before or with this deploy. The server's redeem response now carries
a `bridgeToken` that only the 0.2.0 CLI stores, and the workspace the CLI
scaffolds runs `npx agentdash-connect@latest inbox` — a subcommand that exists
only from 0.2.0. Deploying the server alone strands the new field; publishing
the CLI alone is harmless (older servers return no `bridgeToken` and the CLI
skips the inbox setup cleanly).

## Behaviour Changes

**Redeeming a connect code now connects the inbox too.** A connect code used to
mint only an agent API key — the agent's own identity, which every `/bridge/*`
route refuses, because an agent credential that could read its steward's inbox
would hold authority over the approvals meant to constrain it. The credential
those routes accept, a bridge endpoint bound to the person, had no way to be
created: the enrolment UI was deleted in the same release that fixed the
capability it requests, so "the question lands in your Claude Code" was a
promise over a path with no way to mint its credential. A steward traced both
resulting 403s and asked the right question.

Redeem now also creates an enrolled endpoint — bound to the code's CREATOR,
never the unauthenticated redeemer, with the read and inbox capabilities — and
returns its token once. The 0.2.0 CLI stores it at `~/.agentdash/bridge-token`
(mode 600), scaffolds `~/agentdash-inbox` with a SessionStart hook, and answers
`agentdash-connect inbox` with the same rendering, ordering and never-exit-2
rules as `paperclipai bridge inbox`.

This deliberately widens what a connect code yields: it now also delegates the
creator's inbox, decision handles included. The boundary is unchanged — ten
minutes, single use, rate-limited, audited, revocable per machine.

**Agent keys are no longer offered the bridge tools.** All eight only ever
answered a control-plane credential with 403; a steward counted them in
tools/list and reasonably read the failures as a broken instance. Two
credentials, two disjoint tool surfaces.

## Validation

The full loop was proven pre-release on the MK host against real embedded
Postgres, through the real actor middleware: redeem → endpoint → sync →
decision handle → decide once → replay refused → revoke → shut out; and the
agent key from the same redemption refused by the inbox. A clean-profile
rehearsal of the real CLI paired both credentials at mode 600 and read the
inbox through the scaffolded hook's own command. Evidence:
`~/.agentdash/verify/bridge-validation-20260914/` on the MK host.

Not yet exercised anywhere: a real Claude Code session firing the SessionStart
hook, and any Windows machine. The first steward on Windows is the first
Windows pass.

## Known follow-up

There is still no UI to list or revoke a user's connected machines; revocation
works via the API and is covered by the loop tests.
