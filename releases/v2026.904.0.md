# v2026.904.0

> Status: release candidate, not yet cut. Version date 2026-09-04 (the cut
> pins `stable_date` to it); the release date replaces this line when the cut
> lands.

Thirty-four squashes past v2026.902.0. Four migrations, all forward-only.
This release subsumes the v2026.902.1 candidate, whose notes were merged on
2026-09-02 but whose cut was cancelled at the gate; everything that candidate
carried is in this one. Every runtime change below was exercised against a
running internal instance in a disposable company before inclusion, and the
evidence is recorded on the AGE board.

## Behaviour Changes You Must Read First

**This release carries four migrations, and there is no way back by code
alone.** `0123_funny_the_stranger` adds provenance columns to agent API keys
and backfills existing keys named `default` that were minted with their agent.
`0124_steward_inbox` creates the three steward-inbox tables: the event log,
per-steward sequences, and per-machine cursors. `0125_steward_inbox_decisions`
adds a nullable bridge-endpoint column to channel callback tokens so an
approval can be resolved from the inbox. `0126_inbox_connect_actions` adds the
single-use action-handle table and a nullable check-interval column on bridge
endpoints. Everything after `0123`'s backfill is additive — no existing row is
touched — but Drizzle has no down-migrations. Rolling this release back means
restoring the database backup taken before the update and losing whatever was
written since. The OTA updater refuses a migrating release unless run with
`--allow-migrations`; that refusal is correct, read it before overriding it.

**A Hermes run that lets Hermes decide for a human now fails.** Hermes's
built-in `clarify` tool is a terminal prompt. Nobody is at that terminal in a
headless run, so it can only time out, and Hermes's fallback told the agent to
"use your best judgement and proceed". Such a run used to report success. It
now ends `failed` with `errorCode: human_question_unanswered`, the run log says
why, and the agent is told in its prompt to raise an `ask_user_questions`
interaction instead. Expect some previously "successful" runs to start
failing; each one is a question a person never received. The guard now also
covers Hermes's builtin code path directly, closing the hole where a builtin
invocation bypassed the wrapper's check.

**Existing agents' generated mandates get smaller on their next run.**
Integration guidance (SharePoint, Gmail, Slack, the MSP demo) is now opt-in
skills rather than pages of every agent's `AGENTS.md`, and the refresh service
withdraws generated blocks the source no longer carries instead of leaving them
in place forever. An agent can also drop a generated block it has no use for,
per agent rather than per company. Human-authored prose outside the generated
blocks is untouched. One design-partner agent's mandate had reached 53 KB of
verbatim default; that is the case this fixes.

## The Steward Inbox

A steward now receives agent updates and approval requests inside their own
Claude Code or Codex workflow, and can act without opening the board.

- **A durable log with a per-machine cursor.** Inbox entries persist per person
  and each connected machine tracks what it has seen, so a steward who reads on
  two machines is not re-served old entries on either.
- **Approvals resolve from the inbox.** A steward can approve or refuse an
  agent's pending approval request from the same surface that delivered it.
- **An ordered digest.** Entries arrive as an ordered digest rather than an
  unordered flood.
- **Reading and acting work end to end.** The inbox is readable and actionable
  from the client, not only writable by agents.
- **A steward can direct work and set a preference from the same surface.**
  Naming an agent and a task ("have Casper draft the agenda") resolves the
  agent, reads the assignment back, and acts only when the person confirms a
  single-use handle bound to that machine — nothing happens on the strength of
  a sentence alone, and a name that does not resolve comes back as a question,
  never a guess. The same propose-then-confirm shape governs the one
  preference offered (check every 30 or 60 minutes). Across this release the
  endpoint credential's allowlist grows from three routes (poll, result,
  decline) to nine — the six inbox routes for sync, ack, decide, agents,
  propose, and confirm — with no new authority: permission is re-checked when
  the handle is redeemed, a handle is inert on any other machine including
  the same person's second one, and the work is attributed to the person,
  never the machine.
- **The connect panel tells the truth.** Connecting a machine now explains what
  the bridge does before the steward runs anything, and the printed enrollment
  command is one that starts: it names the real CLI (`paperclipai bridge run`)
  and carries the `--egress` flag the CLI requires. A stale tab left open
  across a deploy no longer hard-fails in a way that looks like a product bug,
  and the chunk-load window behind that class of failure is closed.

## Governance Reaches the Runtime (Hermes)

- **Steward directives are delivered.** The external Hermes adapter never
  rendered `paperclipAgentDirectives` into its prompt, so directives persisted,
  reported as pushed, and never reached the agent. They now render into every
  Hermes run in a fixed order: mandate, directives, harness rules, task. Where
  a directive and the mandate disagree about *how* to work, the directive wins;
  it never outranks the harness rules that follow it and cannot grant
  capability. A steward's template braces survive the pass.
- **A push says whether it will be seen.** `POST …/directives` returns
  `delivery` (`adapterType`, `delivered`, `via`, `detail`) plus a `warnings`
  entry when the agent's adapter cannot render directives. "Pushed" is no
  longer mistaken for "applied".
- **Instructions are edited as source.** The mandate an agent runs is editable
  as the source document it is, with the change reaching the next run.
- **A Hermes agent works in its own workspace.** With no working directory
  configured, the Hermes adapter fell through to the server's own checkout, so
  a coding agent could leave hundreds of lines of uncommitted work in the
  directory the server was serving from — which then blocked the next deploy
  on a dirty tree. Hermes now runs in the workspace the runtime resolves (the
  project worktree when the task has one, the agent's own home otherwise), as
  the Codex and Claude adapters already did; an explicitly configured working
  directory still wins.

## Honest Surfaces

- **A wrong method on a known route answers 405** with an `Allow` header
  computed from the router itself. Unknown paths still answer 404.
- **Every agent API key records what minted it** — agent creation, onboarding,
  a connect code, or a person at the keys panel — with the creating user or
  agent where there was one. The keys panel says so in words, and the
  agent-creation response marks its bundled key `autoCreated: true`.
- **The sandbox is documented as it is.** `doc/AGENT-SANDBOX.md` records the
  four-variable control surface, its `off` default, and the measured minimum
  confinement for a uv-managed Hermes.

## Logs Stop Recording Credentials

- **The session cookie no longer reaches `server.log`.** The HTTP logger
  wrote every request's headers verbatim, so the browser session cookie was on
  disk in plaintext on every logged request, successful ones included; anyone
  who could read the log, a log shipper, or a backup that contained logs could
  replay the session. The cookie header is now redacted at the logger, on
  every line. This was present in every earlier release, v2026.902.0
  included, and upgrading closes it going forward only: the lines already
  written stay on disk. Rotate or delete the old log, and if it has been read
  by anyone who should not hold a session, have the people in it sign out and
  back in.
- **Error lines redact credential-shaped fields.** On 4xx/5xx lines the logger
  copies the request body, params, and query so an operator can diagnose the
  failure. Passwords, tokens, API keys, and their relatives inside those
  payloads now appear as `[REDACTED]` instead of their value, so a mistyped
  password at sign-in no longer lands in the log. (Upstream Paperclip #8013,
  cherry-picked unchanged.) Still in clear on error lines: the request URL,
  query string included, so a credential passed as a query parameter is still
  logged there; that is tracked as follow-up work rather than claimed here.

## Fixed Since This Candidate Was First Prepared

Three limitations named in the v2026.902.1 notes are fixed in this release:

- **The OTA update button honours the server's `canApply` verdict.** A release
  the updater will refuse can no longer be approved from the page.
- **Company delete clears every agent-referencing table.** Deleting a company
  that used directives, the bridge, or any of the nineteen agent-linked tables
  no longer fails on a foreign key.
- **Per-agent `adapterConfig.env` values reach a Hermes child correctly.**
  Plain secret envelopes are unwrapped instead of arriving as the stringified
  object; secret references are dropped with a named log line.

- `fast-uri` is pinned past the three high-severity advisories that were

## Known Limitations, Stated Plainly

- **An inbox cadence change is stored but inert.** The scheduler that would
  read `check_interval_minutes` is not built, so the preference has no effect
  yet; the readback and confirmation both say so, and it must not be described
  to customers as working until the scheduler lands.
- The clarify fallback is refused after the run, not interrupted during it:
  the adapter exposes no child pid to the wrapper. Delivering the question to
  the steward's inbox and bridge is separate work.
- A confined `hermes_local` run completing a real model turn (AGE-33) has not
  been executed; exec and exit under confinement were.
- OTA signatures are still not verified; provenance means the tag is on `main`.
- Runtime/model reporting can still read stale environment rather than the
  Hermes-selected runtime (AGE-1).

## Upgrade Guide

This is an in-place upgrade. Preserve the existing database, configuration,
storage, and agent data; do not reinstall or reimport the instance.

1. Back up the database first (`paperclipai db:backup`). This release cannot
   be rolled back without it.
2. Apply. On the OTA path, pass `--allow-migrations` deliberately; on the
   source path, let the normal startup migration apply `0123` through `0126`
   (they complete in under a second on a typical instance).
3. Confirm `GET /api/health` reports `status: ok`, then the post-install
   checks: `POST /api/health` answers 405 with `Allow: GET, HEAD`; a new
   agent's creation response carries `apiKey.autoCreated: true`; the
   enrollment page shows `paperclipai bridge run` with its required flags;
   and after one signed-in page load, the newest request line in
   `logs/server.log` carries `"cookie":"[Redacted]"` rather than a session
   token.
4. To roll back: move code back with the rollback wrapper, **then restore the
   pre-update backup**. Keys minted after the upgrade lose their provenance,
   and inbox entries, cursors, and action handles written since the upgrade go
   with the restore; nothing else is lost beyond what was written since.

Existing `default` keys minted within two minutes of their agent are attributed
to agent creation by the backfill; keys a person named `default` later stay
`manual`.
